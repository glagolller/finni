# Совместная работа

## Ветки

`main` хранит согласованные документы и позднее проверенное приложение. Ветки `frontend/<задача>` — работа интерфейса, `logic/<задача>` — логика/хранение и принадлежащая Л общая конфигурация. Первую историю с документами создаем один раз здесь; друг клонирует общий репозиторий, а не выполняет независимый git init.

Перед задачей: проверить `git status`, сохранить свою работу и получить обновления `main`. Не выполнять обновление поверх неразобранных изменений. Новую рабочую ветку создавать от актуального `main`. После задачи: просмотреть diff, добавить только относящиеся к задаче файлы, сделать коммит, отправить ветку и открыть PR.

PR — предложение объединить изменения. В описании указать результат, ID требований, проверки, ограничения и изменения контракта. Вторая сторона просматривает; сливать после подходящей проверки. Пока кода нет, проверяется документация; после появления приложения нужна также сборка/тесты по изменению. Защита ветки на GitHub пока не включена — это рабочее правило, а не настроенное ограничение.

## Владение

Ф: UI, ресурсы оформления, навигация, тестовый UI-адаптер, интерфейсные проверки и свой журнал. Л: модели/экономика/хранение/контент, контракт после согласования, проверки логики и свой журнал. Л предложен владельцем Android, pubspec и lock-файла; ждать подтверждения. Версионный lock-файл приложения впоследствии сохранять в Git.

Совместный контракт изменять согласованно. При конфликте читать обе стороны, не выбирать вслепую одну версию. Не переписывать историю и не выполнять force push. Рабочие изменения объединять ежедневно.

## Отчетность

После задачи обновить матрицу и личную запись с датой, коммитом, артефактами и фактическими проверками. История коммитов должна отражать настоящую последовательность. Личные реквизиты и готовые документы с ними хранить вне общего репозитория.
