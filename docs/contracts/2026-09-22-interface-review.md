# Проверка предложения logic_contract_v0.1 стороной интерфейса

22.09.2026. Источник: FINNI_RESPONSE_TO_INTERFACE.md, получен от участника Ф. Это проверка проектной спецификации, не тест готового приложения. Исходный файл хранится вне репозитория. Изменения ниже предлагаются для одного завершающего согласования; приложение пока не создается.

## Принято со стороны Ф

- Flutter/Dart, SQLite через sqflite, локальный JSON-контент, Android API 26+, без сервера.
- Л владеет общим Flutter-каркасом, Android-конфигурацией, зависимостями, lock-файлом, реализацией контрактов и выпуском APK. Ф владеет UI и подключением сервисов.
- Асинхронные методы, отдельные preview/command, атомарность, actionId и stateRevision.
- finishPeriod закрывает период, startNextPeriod отдельно начисляет следующий доход.
- Покупка сверх плана при достаточных деньгах разрешается с отдельным предупреждением. Превышение общей доступной суммы в самом плане — блокирующая ошибка. Эти ситуации не путать.
- success в ActionResult означает успешное применение команды, а не правильность решения ребенка. UI нужен отдельный результат задания.
- Диапазоны satiety/mood 0–100, настроение отдельно от стадии; семантические ID ресурсов.
- Предложенные 8 цен, 3 цели, доход 100, награда 5, пороги роста 6/12 принимаются как базовый расчетный пример, с устранением проблем ограниченности ресурсов и определения заданий ниже.

Проверка пяти строк демонстрационного расчета: конечные пары (доступно, накопления) равны (30,30), (25,60), (5,90), (15,115), (5,25). Арифметика сходится; сумма доходов 500, наград 30, покупок 380 и списания цели 120 дает конечные общие деньги 30. Это арифметическая проверка документа, не выполненный игровой сценарий.

## Исправления до фиксации API

### 1. Дополнить модели и точные параметры

В Profile.displayName допускается отсутствие значения, а в PetState нет имени питомца. Добавить обязательное игровое petName и соответствующее поле createProfile. Реальное имя ребенка не запрашивается.

Для главного экрана нужен активный/рекомендуемый TaskSummary и доступные задания с причинами недоступности. Для выбора покупок и целей нужны методы чтения каталога, для стартового выбора режима — определенный способ найти normal/demo профиль без неизвестного UI идентификатора. Описать их в контракте, не заставлять UI читать JSON или БД напрямую.

Сейчас список имен методов есть, но точные payload большинства команд, GoalProgress, ProfileSettings, WarningMessage и результат getProgress не заданы. Зафиксировать обязательные поля, допустимые null и варианты ответов на задания. Разделить нулевую сумму категории бюджета (допустима) и нулевую сумму перевода (ошибка).

### 2. Задания должны быть действиями, а не только ответами

Таблица шести тем пока не определяет интерактивные сценарии. Для каждого задания задать тип действия (распределение сумм, корзина покупок, перевод/сравнение накоплений и т.п.), входные параметры, критерий, объяснения обоих исходов. Набор викторин не покрывает ТЗ §2.5.8.

Добавить TaskAttemptResult: taskId, результат correct/needs_retry, explanation, rewardGranted, remainingAttempts и состояние награды. Не определять правильность по success или общему reasonCode task_try. Указать, учебное действие симуляционное или меняет настоящий бюджет: нельзя неявно списывать реальные игровые деньги и при задании, и при обычной операции второй раз.

Если третье новое задание решено верно в периоде при лимите двух наград, определить судьбу награды. Предложение Ф: отметка изученного сохраняется, награда становится отложенной и выдается один раз в следующем периоде в пределах лимита, с явной причиной. Допустим и более простой вариант ограничения наград, но правила должны быть однозначны, видимы ребенку и соответствовать обязательной доступности заданий демо. Не оставлять заблокированное задание после пятого периода без объяснения и доступного действия сброса.

### 3. Ограниченность ресурсов пока не доказана

Сумма цен 320 больше нового дохода 110, но остаток переносится без ограничения. Если завершать периоды без покупок, к четвертому периоду доступно 400, и можно купить весь каталог. Снятие накоплений также увеличивает доступные средства. Поэтому сравнение только 320 и 110 не подтверждает принцип §2.1 ТЗ для произвольного состояния.

Л должен предложить одно простое правило ограниченного расходуемого ресурса/ассортимента периода без исчезновения сбережений и проверить контрпример с большим переносом. Если предполагается трактовка требования только для демонстрации, это нужно явно подтвердить у постановщика, а не объявлять соблюдение всех состояний доказанным. Не добавлять решение этого вопроса скрыто в UI.

### 4. Формулы состояния и план с ошибочным выбором

Для satiety/mood есть диапазоны, но отсутствуют начальные значения как правило, числовые эффекты покупок/заданий/завершения периода и тексты причин. Задать их таблицей, чтобы expectedPetDelta можно было вычислять и проверять. Ошибка должна оставаться спокойной и обратимой.

Обязательное отклонение плана при needsLimit ниже стоимости набора — дополнительное ограничение, которого нет в ТЗ. Ф предлагает вместо блокировки предупреждение о недостатке на необходимое с возможностью осознанного подтверждения и последующим восстановлением; жестко блокировать только некорректные суммы и превышение доступного бюджета. Если Л оставляет жесткий минимум, нужен отдельный убедительный сценарий самостоятельного финансового выбора и ошибок. Не запрещать ребенку все учебные ошибки заранее.

### 5. Повтор результата не должен откатывать UI

Сохраненный результат replayed может содержать старый stateSnapshot. Например, действие A сохранило ревизию 3, действие B — 4, затем повтор A вернул 3. Ф не должен заменить актуальный экран ревизией 3.

Предложение: повтор возвращает исходный исход операции, но текущий достоверный stateSnapshot; UI не воспроизводит повторно награды/анимации для replayed и никогда не применяет меньшую ревизию к тому же профилю/поколению. Если выбран возврат исходного снимка, отдельно определить обязательное актуальное чтение перед дальнейшими действиями. Уточнить область уникальности actionId, профиль и тип команды в сравнении, поведение повторов delete/reset после очистки записей. Для reset важно не допустить принятия старой команды в новое игровое состояние.

### 6. Полные согласованные фикстуры

В документе прямо указано, что JSON сокращен. До написания тестового адаптера нужны полные сериализуемые примеры, соответствующие одним и тем же определениям полей. Сейчас неполны снимки, PetDelta и обязательное createdAt; это допустимо для иллюстрации, но не для проверки контракта.

Добавить отдельные снимки закрытого периода, отсутствующего профиля, завершенного демо, stale_state и снятия с подтверждением. Каждый независимый пример снабдить исходным состоянием; одинаковая ревизия у разных примеров не означает одну последовательность.

### 7. Дополнить демонстрацию

Пять периодов рассчитаны, но еще нужны явные шаги попытки покупки при нехватке денег, перезапуска с проверкой сохранения и входа взрослого со сбросом. Это требования приложения А. Пример: после действий периода 1 баланс 30 — попытаться купить музыкальную игрушку за 70, показать недостачу 40, сохранить исходные деньги/историю. Добавить ожидаемые состояния до/после. Проверить отдельно повторное начисление и отсутствие автоматического роста на плохой серии.
