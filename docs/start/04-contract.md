# Проект договора между интерфейсом и логикой

Статус: предложение версии 0.1, не утверждено и не реализовано. Это локальный программный интерфейс, не HTTP API. Ф и Л согласуют его до кода. OpenAPI нужен только при решении добавить сервер.

## Данные

| Модель | Минимальные сведения |
| --- | --- |
| Profile | Локальный ID, игровое имя, внешний вид, режим demo/normal, версия схемы |
| GameState | Профиль, период, доступный баланс, накопления, цель, состояние/стадия питомца, активное задание |
| BudgetPlan | ID периода, суммы трех направлений, черновик/подтвержден, исходная доступная сумма |
| BudgetActual | Фактические обязательные/необязательные расходы, фактические пополнения; правила учета снятий описаны отдельно |
| Item | ID, детское название, категория, целочисленная цена, ожидаемый эффект, ID изображения |
| Goal | ID, название, стоимость, накоплено, остаток; правила достижения/смены цели |
| Task | ID, тема, навык, тип интерактивного сценария, параметры, критерии, объяснения, награда |
| Pet | Внешность, текущие показатели, стадия развития и причина последнего изменения |
| Transaction | ID операции, период, тип, сумма, источник/предмет, изменения доступных денег и накоплений |
| PeriodSummary | Подтвержденный план, факт, обязательные потребности, пополнения, причины прогресса, следующий шаг |
| LearningProgress | Завершенные задания, пройденные темы, итоги и прогресс цели |
| ActionResult | Успех/ошибка, новое состояние, изменения денег и питомца, код причины, объяснение, доступные следующие действия |

## Предлагаемые действия

| Действие | Вход | Выход/ограничения |
| --- | --- | --- |
| loadState | Нет | Сохраненное состояние либо отсутствие профиля; ошибка чтения отдельна |
| createProfile | Игровое имя, ID внешности | Новый локальный профиль; стартовая сумма со своим источником |
| previewBudget / confirmBudget | ID периода, три суммы | Остаток/ошибки; подтвержденный план хранится отдельно от факта |
| previewPurchase / buyItem | ID предмета, период, ID действия | Цена/эффект; при нехватке никаких списаний |
| selectGoal | ID цели | Цель и правила переноса накоплений; не терять их молча |
| previewTransfer / transferSavings | Направление, сумма, подтверждение | При снятии явный предпросмотр уменьшения; атомарное изменение двух остатков |
| submitTaskAction | ID задания, содержательное действие, ID попытки | Последствия, объяснение, награда; защита от повторного начисления одного результата |
| finishPeriod | ID периода | Сопоставление плана/факта, изменение развития, следующий период |
| getHistory / getProgress | Период/фильтр | Данные без самостоятельного пересчета UI |
| resetDemoProfile | Подтверждение | Детерминированное исходное демосостояние |
| deleteProfile | Подтверждение | Удаление относящихся к профилю данных, выход на первый запуск |
| updateSettings | Настройки | Сохраненные предпочтения |

## Инварианты

1. Монеты целочисленные. Недопустимы отрицательные суммы, отрицательные остатки и распределение сверх доступного бюджета.
2. Перевод в накопления уменьшает доступный баланс на ту же сумму. Обратный перевод требует подтверждения. Это перемещение ресурсов, а не новый доход.
3. Подтверждение плана не является покупкой/переводом. План сохраняется для сравнения с фактом.
4. Отмена и неуспех не изменяют деньги, историю или прогресс. Повторное нажатие не дублирует финансовую операцию.
5. UI не рассчитывает награды и рост, не записывает напрямую БД. Логика проверяет данные независимо от клиентской формы.
6. Логика возвращает причины изменений. Ф отвечает за понятное представление, Л — за правильность смысла.
7. Удачное финансовое действие и его сохранение согласованы; UI не сообщает об успехе при неподтвержденной записи. Ошибка хранения не должна приводить к тихому сбросу профиля.
8. Демо использует те же правила экономики; ускоряется время/доступность, а не подменяется расчет. Сброс демо не уничтожает обычный профиль без явного выбора пользователя.
9. Необязательная покупка не обязана считаться ошибкой; ошибка определяется ресурсами и последствиями, а не наличием «неправильной» кнопки.

Это инженерные предложения команды для исполнения ТЗ, а не дополнительные пункты организатора.

## Что требуется согласовать

- Правила периода: старт, доход, завершение, перенос остатка, учет дохода после подтверждения плана.
- Экономика: обязательные потребности, цены, награды, достижимость целей и отсутствие бесконечного фарма.
- Смена/достижение цели и учет снятий в плане/факте.
- Порог и частота изменения трех стадий; связь с обязательными расходами, планом/фактом и регулярностью накоплений.
- Способ хранения, версии схемы, восстановление после ошибок и техническая сборка.

После согласования каждый записывает принятое решение и идентификатор версии контракта. Если ответ другой стороны не получен, допустимы макеты и тестовые данные с маркировкой; зависимую несовместимую реализацию не выдавать за интегрированную.
