# Правила совместной работы

Это организационное соглашение проекта. Два Codex на разных ПК не имеют общей переписки и не синхронизируют контекст автоматически. Источник согласованных решений — файлы и история общего репозитория. Файлы текущего пакета предназначены для переноса в него после настройки; репозиторий пока не создан.

## Ветки и ежедневная работа

1. Один участник создает репозиторий, второй получает доступ и клонирует его. Способ доступа жюри подтверждается отдельно; режим видимости выбирают с учетом конкурсных материалов.
2. `main` содержит последнюю совместно проверенную версию. Предлагаемые рабочие ветки: `frontend/<задача>` и `logic/<задача>`.
3. Перед новой задачей получить изменения `main`, проверить локальные незакоммиченные изменения и прочитать контракт, журнал решений и актуальную матрицу.
4. Сделать небольшой законченный результат своей зоны, выполнить подходящие проверки, обновить личный журнал и сохранить нормальный коммит с фактическим содержанием.
5. Передать результат через запрос на слияние (PR) или согласованное слияние ветки. В сообщении: что изменено, требования, проверки, ограничения, влияние на другую сторону.
6. До слияния проверить, что приложение собирается и согласованный общий сценарий не сломан. Не считать одни скриншоты доказательством интеграции.
7. Ежедневно объединять готовые части. Не откладывать первое подключение до последнего дня.

Не переписывать историю ради имитации другой последовательности работ, не придумывать даты или авторство. При конфликте читать обе версии и сохранять оба нужных изменения. Запрещено автоматически разрешать все конфликты выбором одной стороны, делать force push в общую ветку или стирать чужую работу.

## Предлагаемые владельцы файлов после выбора Flutter

| Область | Владелец | Правило |
| --- | --- | --- |
| `lib/ui/`, визуальные ресурсы, `docs/ux/` | Ф | Экраны, навигация, отображение состояния, формы и интерфейсные проверки |
| `lib/domain/`, `lib/data/`, `assets/content/`, тесты экономики | Л | Расчеты, модели хранения, контент, деморежим, сохранение |
| `lib/contracts/`, `docs/contracts/` | Л ведет после совместного согласования | Изменение формы данных/сигнатур — через согласованный запрос; Ф проверяет потребителей |
| `android/`, зависимости, lock-файл, настройки сборки | Л, подтвердить | Ф отправляет запрос на нужную зависимость; одновременных несогласованных правок нет |
| Точка запуска и связывание UI с сервисами | Ф, подтвердить | Л предоставляет реализацию контрактов; сборочные настройки остаются у Л |
| `docs/practice/frontend/`, `evidence/frontend/` | Ф | Личные материалы Ф |
| `docs/practice/logic/`, `evidence/logic/` | Л | Личные материалы Л |
| Общая матрица и архитектура | Ф+Л, один редактор за раз | Сверять версии перед изменением; статусы подтверждать доказательствами |
| Финальная упаковка/версия/тег | Л готовит, К сдает | Отчет о проверке конкретного передаваемого APK |

Все пути в этой таблице — предложение структуры будущего приложения. Эти каталоги с кодом сейчас не создаются. Общие тексты лучше править небольшими отдельными изменениями; для дневных записей использовать отдельные файлы, чтобы избежать конфликтов.

## Работа с контрактом

Ф отправляет запрос: какие данные или действие нужны экрану, требование, пример входа/выхода, состояние ошибки. Л подтверждает либо предлагает альтернативу. Принятое решение записывают с датой и версией. Изменение несовместимого контракта включает план обновления обеих сторон; старый интерфейс не удаляют внезапно.

Временный UI на тестовых данных допустим, но явно отмечается в журнале и сборке разработки. Финальная приемка проводится с настоящей логикой. UI не содержит вторую копию экономики, чтобы скрывать отсутствие функций Л.

## Что обновляется после задачи

- Связанные ID требований: статус, проверка, реальная ссылка на доказательство.
- Личный журнал: фактическая дата, работа, результат и чему участник научился/что проверил.
- Снимок результата: макет, скриншот, схема, тестовый протокол или сборка согласно типу задачи.
- Инструкция запуска, если она изменилась; лицензии для новых ресурсов.
- Сообщение другой стороне, если меняется договор взаимодействия или есть блокер.

Формы записей в `10-evidence.md`. Не хранить пароли, подпись APK, личные заполненные бланки и конфиденциальные источники в общем открытом репозитории. Итоговые файлы практики с реквизитами удобно хранить отдельно от публикуемого кода. Наличие исключения в `.gitignore` не удаляет уже опубликованный секрет из истории.

## Кто что делает руками

Агенты могут готовить код и документы, проверки и инструкции. Участники утверждают продуктовые решения, фактически проверяют приложение на доступном телефоне, разбирают свою часть для защиты и подтверждают сведения о выполненных действиях. Непроведенный тест не становится пройденным по прогнозу агента. Подписи и оценка принадлежат руководителям.
